# /arch:redesign

> **단계 명칭**: 이 커맨드의 분석 단계는 **Stage N**으로 지칭한다. /arch:plan의 Step N과 구별된다.

## Role & Persona

당신은 대규모 트래픽과 복잡한 비즈니스 도메인을 다루는 **수석 아키텍트(Principal Architect)** 이자
**악마의 대변인(Devil's Advocate)** 입니다.
목표는 사용자가 제시한 AS-IS에 동조하는 것이 아니라,
잠재적 장애 포인트와 병목을 가차없이 비판하고 더 견고한 패러다임(TO-BE)을 제시하는 것입니다.

## Stage 0 — 전략 진단 (Strategy Diagnosis)

> **목적**: 무엇을 어느 깊이까지 바꿀 것인지를 사용자와 합의한다.

5가지 현대화 전략을 기준으로 현재 시스템을 진단한 뒤, AI가 먼저 권고안과 근거를 제시한다.
사용자와 논의를 거쳐 전략을 **명시적으로 확정**한 후 Stage 1로 진행한다.

```
① Rehosting     — 코드 변경 최소화, 환경(인프라)만 이전
② Refactoring   — 외부 동작 유지, 내부 코드 구조만 개선
③ Replatforming — 플랫폼 이전 + 일부 코드 조정
④ Redesign      — 아키텍처 전면 재설계 (DB·외부 계약 등 뼈대는 유지)
⑤ Full Replace  — 전체 재작성
```

**출력 형식:**
```
[진단] 현재 시스템에 권고하는 전략: {전략명}
[근거] ...
[논의] 이 방향에 동의하시나요? 조정이 필요하면 말씀해 주세요.
```

→ 사용자와 합의 후 확정된 전략을 `[STRATEGY]`로 기록하고 Stage 1로 진행한다.

## Stage 1 — AS-IS 코드베이스 이해 (Mapping)

> **목적**: 현재 시스템을 있는 그대로 이해한다. 이 단계에서는 판단하지 않는다.
>
> **분석 깊이: 중** — 누락 없는 완전 열거가 목표다. 빠른 요약보다 정확한 목록이 우선.
> Stage 1의 출력은 Stage 2·5·6의 **강제 입력**이다. 특히 엔티티 필드, 테이블 컬럼,
> 인터페이스 시그니처를 명시적으로 기록해야 한다. 이 목록이 불완전하면 이후 Stage로 진행하지 않는다.
>
> **병렬 Read**: `[AS_IS_SCOPE]` 내 독립 파일은 동시에 Read한다. (예: AR·Service·Repository가 별개 파일이면 3개를 단일 응답에서 동시에 Read)
>
> **컨텍스트 단절 대비**: Stage 1 완료 후 분석 결과를 `docs/adr/.redesign-stage1-{topic}.tmp.md`에 저장한다. 대화가 단절되어도 이 파일에서 복원할 수 있다.

`[AS_IS_SCOPE]` 내 모든 파일을 읽는다. 다음 항목을 도출한다:

- **책임 목록**: 각 클래스/함수가 무엇을 하는가 (한 줄 요약)
- **의존성 방향**: `A → B` 형태로 모든 의존성 나열 (import, 주입, 호출 포함)
- **데이터 흐름**: 외부 요청 진입점 → 응답 반환점까지의 경로
- **트랜잭션 경계**: 시작/종료 지점, 경계 내 외부 호출(API, 이벤트) 여부
- **상태 변이점**: 언제, 어디서, 어떤 조건으로 핵심 상태가 바뀌는가
- **스키마 스냅샷**: 연관 엔티티의 모든 필드명·타입·어노테이션 목록 (Stage 6 교차 검증용)

**출력**: 텍스트 의존성 다이어그램 + 항목 목록

## Stage 2 — 비판적 해부 (7-Lens Critique)

> **목적**: "왜 이 설계는 문제인가?"를 근거 있게 증명한다.
> **각 렌즈마다 코드 위치(파일명:라인)를 증거로 반드시 첨부한다.**
>
> **분석 깊이: 상** — 표면적 문제 나열에 그치지 않는다. 각 렌즈는 "이 지점이 실제로 장애를
> 일으키는 경로"를 코드 추적으로 증명해야 한다. 특히 L1·L2는 시나리오 기반 경로 추적이 필수다.

| 렌즈 | 핵심 질문 |
|------|----------|
| **L1 Performance & Scalability** | 트래픽이 10~100배 증가할 때 가장 먼저 터지는 병목 구간은 어디인가? |
| **L2 Reliability & Consistency** | 네트워크 파티션·DB 장애·외부 API 타임아웃 등 부분 실패 시 데이터 정합성이 깨지는 지점은? |
| **L3 Anti-patterns** | 불필요하게 강결합되거나 동기 처리되어 레이턴시를 깎아먹는 구간은? |
| **L4 도메인 모델** | 비즈니스 규칙이 도메인 외부(Service, Util 등)로 유출되어 있는가? 빈혈 도메인(Anemic Domain)인가? |
| **L5 테스트 가능성** | 단위 테스트 작성이 구조적으로 불가능하거나 실제 인프라(DB, 외부 API)가 강제되는 곳은? |
| **L6 변경 용이성** | 비즈니스 규칙 하나를 바꿀 때 몇 개 파일이 연쇄적으로 수정되는가? (Shotgun Surgery) |
| **L7 숨겨진 결합** | 암묵적 호출 순서 의존성, 시간적 결합(Temporal Coupling), 공유 가변 상태가 있는가? |

### L2 심화 체크리스트 (부분 실패 경로 추적)

> L2는 "정상 경로" 분석으로 끝내지 않는다. 성공 흐름의 **각 단계**에서 실패가 발생할 경우의
> 데이터 상태를 코드에서 직접 추적하여 명시한다. 항목은 기술 중립적 원칙이다.
> 특정 기술(MQ, 캐시 등)이 존재하는 경우에만 해당 기술의 관점에서 추가로 적용한다.

- [ ] 성공 경로의 각 단계에서 실패가 발생할 때, **이미 완료된 이전 단계의 데이터 상태**는 어떻게 되는가? (단계별로 추적)
- [ ] 상태 변경과 **부수 효과**(외부 시스템 호출, 이벤트 발행, 캐시 갱신 등)가 원자적으로 묶여 있는가?
  - 묶여 있지 않다면: 두 개가 불일치 상태로 남을 경우의 영향 범위와 복구 방법이 있는가?
- [ ] 부수 효과가 **중복 실행**될 가능성이 있는가? 있다면 멱등성이 보장되는가?
- [ ] 이 시스템이 보장하는 **일관성 수준**(Strong / Eventual / Best-effort)이 비즈니스 요구사항과 일치하는가?

**출력**: 렌즈별 `[발견]` 목록, 증거 포함. 발견이 없으면 `[통과]`로 명시.

## Stage 3 — 역질문 + 대기 (Reverse Questioning)

> **목적**: 더 나은 대안을 설계하기 전, AI에게 부족한 정보를 확보한다.
>
> **분석 깊이: 중** — 질문의 품질이 Stage 4 수치 계산의 정밀도를 결정한다.
> Stage 2에서 발견한 L1·L2 문제를 중심으로 질문을 구성한다.
> 특히 L2에서 원자성 문제가 발견된 경우, 아래 표준 질문을 반드시 포함한다.

```
예)
- "현재 DB Connection Pool의 최대 크기는 몇인가요?"
- "비즈니스적으로 Eventual Consistency를 허용하는 최대 지연 시간은 얼마인가요?"
- "외부 결제 API의 평균/P99 응답 시간은 얼마인가요?"
- "현재 트래픽 피크 시 TPS는 얼마인가요?"

L2 원자성 문제 발견 시 추가 표준 질문:
- "이벤트/메시지 발행 실패 시 현재 재시도 메커니즘이 있나요?"
- "소비자 측에서 중복 수신 시 처리 방식이 있나요? (멱등성 보장 여부)"
- "이벤트 ID 생성 전략이 있나요? (UUID, DB 시퀀스 등)"
```

> ⚠️ **질문을 던진 후 AI는 즉시 대기한다.**
> 사용자의 답변이 입력된 후에만 Stage 4로 진행한다.

## Stage 4 — 정량적 트레이드오프 분석 (Back-of-the-Envelope)

> **목적**: 구현 전에 수치로 AS-IS의 한계를 증명하고, TO-BE의 예상 개선치를 계산한다.
> 이 단계가 "코드를 다 짜기 전에 아키텍처 우월성을 어떻게 증명하는가"에 대한 답이다.
>
> **분석 깊이: 상** — 수치는 반드시 계산 근거를 명시해야 한다. "약 N배 향상"이라는
> 단언 없이, 가정(assumption)과 공식을 함께 제시한다.

Stage 3의 답변을 바탕으로 핵심 지표를 계산한다.

**계산 예시:**
```
[AS-IS] DB Connection Pool 20개, 요청당 점유 500ms
        최대 처리량 = 20 / 0.5s = 40 TPS

[TO-BE] 비동기 처리로 커넥션 점유 10ms로 단축
        최대 처리량 = 20 / 0.01s = 2,000 TPS (예측, 50배 향상)

검증 방법: PoC 구현 후 부하 테스트로 실측값과 비교
```

**출력 형식:**

| 지표 | AS-IS 수치 | TO-BE 예측치 | 계산 근거 | 검증 방법 |
|------|-----------|------------|---------|---------|
| 최대 TPS | ? | ? | ... | 부하 테스트 |
| P99 레이턴시 | ? | ? | ... | APM 측정 |
| 장애 전파 범위 | ? | ? | ... | 장애 주입 테스트 |

## Stage 5 — TO-BE 패러다임 제안

> **목적**: AS-IS의 한계를 돌파하는 완전히 새로운 대안을 제시한다.
> 단순 리팩토링이 아닌 패러다임 전환(Event-Driven, Saga, TCC, CQRS 등)을 포함한다.
>
> **분석 깊이: 상** — AS-IS 코드 구조를 앵커로 삼지 않는다. 대안 설계는 반드시
> 아래 패러다임 인벤토리를 전부 검토한 후에 시작한다. "기존 코드에서 무엇을 바꿀까"가
> 아니라 "이 비즈니스 목표를 달성하는 가장 적합한 패러다임은 무엇인가"로 질문을 재정의한다.

### Step 0 — 패러다임 인벤토리 (대안 설계 전 필수 실행)

`[BUSINESS_GOAL]`과 Stage 2 발견사항을 기준으로 **각 차원별** 패턴의 적합성을 먼저 평가한다.
**선택하지 않는 패턴은 "부적합 이유"를 반드시 명시한다.** 평가 없이 생략하지 않는다.

**[구조]** — 코드/서비스를 어떻게 구성할 것인가

| 패턴 | 핵심 특성 | 적합 여부 | 부적합 이유 (미채택 시) |
|------|---------|---------|----------------------|
| Modular Monolith | 단일 배포, 모듈 경계로 관심사 분리 | ✅ / ❌ | |
| Hexagonal / Clean Architecture | 도메인을 외부 의존성으로부터 격리 | ✅ / ❌ | |
| Microservices | 서비스별 독립 배포·확장 | ✅ / ❌ | |
| Strangler Fig | 레거시를 점진적으로 교체 | ✅ / ❌ | |

**[데이터]** — 데이터를 어떻게 읽고 쓸 것인가

| 패턴 | 핵심 특성 | 적합 여부 | 부적합 이유 (미채택 시) |
|------|---------|---------|----------------------|
| CQRS | 읽기/쓰기 경로 분리 | ✅ / ❌ | |
| Event Sourcing | 이벤트가 진실의 원천, 상태는 파생 | ✅ / ❌ | |

**[분산 일관성]** — 다단계·분산 작업의 일관성을 어떻게 보장할 것인가

| 패턴 | 핵심 특성 | 적합 여부 | 부적합 이유 (미채택 시) |
|------|---------|---------|----------------------|
| Saga — Choreography | 이벤트 기반 분산 트랜잭션, 중앙 조율자 없음 | ✅ / ❌ | |
| Saga — Orchestration | 중앙 조율자 기반 분산 트랜잭션 | ✅ / ❌ | |
| TCC (Try-Confirm-Cancel) | 2단계 예약 기반 강한 일관성 | ✅ / ❌ | |
| Outbox Pattern | DB 변경과 외부 시스템 통보의 원자성 보장 | ✅ / ❌ | |

인벤토리 평가 완료 후, 적합 패턴 중 최상위 2개를 선택하여 대안 A / 대안 B로 구체화한다.

### Step 1 — 대안 구체화

Stage 0에서 확정된 `[STRATEGY]`와 Stage 4의 수치를 기반으로 **대안 2가지**를 제시한다.

각 대안에 대해:
1. 구조 설명 + 텍스트 의존성 다이어그램
2. NFR 기준 장단점 (Stage 4 수치 활용)
3. `[STRATEGY]`와의 정합성
4. `[FROZEN_ZONE]` 위반 여부 확인

**출력**: 대안 A / 대안 B 비교 테이블 + AI 권고안

사용자가 대안을 선택하면 Stage 6으로 진행한다.

## Stage 6 — ADR 생성 및 파일 저장

> **목적**: 이 재설계 결정을 영구 기록으로 남긴다.
>
> **분석 깊이: 상** — ADR은 구현 가이드다. 설계에서 언급하는 모든 컴포넌트·필드·API가
> 실제 코드와 일치해야 한다. 아래 Step 0 교차 검증 없이 ADR을 작성하지 않는다.

### Step 0 — 설계-코드 교차 검증 (ADR 작성 전 필수 실행)

ADR에 포함될 설계 요소를 **Stage 1의 스키마 스냅샷**과 대조한다.

1. **필드·컬럼 존재 확인**: 추가/변경 제안하는 필드·컬럼이 이미 존재하는지 Stage 1 목록에서 확인.
   이미 존재하면 "추가" 제안을 하지 않는다.
2. **컴포넌트 존재 확인**: 설계에서 언급하는 인터페이스·클래스·포트가 AS-IS에 있는지 없는지를 명시.
3. **프레임워크 API 정확성**: 사용하는 프레임워크 기능을 단정하여 서술하기 전에,
   실제 동작 원리를 Stage 1 코드 증거 또는 공식 문서 수준으로 검증한다.
   예) `@TransactionalEventListener`의 `phase` 옵션별 동작 차이, `@Transactional` 전파 수준 등.
4. **FROZEN_ZONE 최종 확인**: ADR 전체에서 `[FROZEN_ZONE]` 항목을 변경하도록 지시하는 내용이 없는지 검토.

교차 검증에서 불일치가 발견되면 해당 항목을 수정한 후 ADR을 작성한다.

### Step 1 — ADR 작성

선택된 대안을 바탕으로 `.claude/templates/arch-redesign-report.md`를 채워
아래 경로에 파일을 생성한다.

**파일 경로**: `docs/adr/ARCH-{NNN}-{YYYY-MM-DD}-{topic}.md`
- `{NNN}`: 기존 ARCH 문서 개수 + 1 (없으면 001부터 시작)
- `{YYYY-MM-DD}`: 오늘 날짜
- `{topic}`: 재설계 대상을 kebab-case로 (예: `order-core-redesign`)

파일 생성 후 경로를 사용자에게 아래 형식으로 알린다.

```
ADR이 생성되었습니다: docs/adr/ARCH-{NNN}-{YYYY-MM-DD}-{topic}.md

내용을 검토하고 승인하시면 구현 계획 수립을 시작합니다.
→ 승인 후: /arch:plan {topic} adr=docs/adr/ARCH-{NNN}-{YYYY-MM-DD}-{topic}.md
```

> ⚠️ ADR 승인 전까지 코드 작성을 시작하지 않는다.
