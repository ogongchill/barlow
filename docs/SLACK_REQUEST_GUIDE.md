# Slack 개발 요청 가이드

AI 티켓 발급 자동화 시스템이 GitHub Issue를 정확하게 생성하려면,
Slack 메시지에 아래 형식과 정보가 포함되어야 한다.

> **원칙**: API 설계(경로/필드/에러 코드), 영향 BC, 테스트 시나리오는
> 개발 단계에서 코드베이스를 보고 결정한다. Slack 메시지에 포함하지 않아도 된다.

---

## 공통 규칙

1. **첫 줄은 반드시 유형 태그로 시작한다.**
    - `[feat]` — 새 기능 추가
    - `[fix]` — 버그 수정
    - `[refactor]` — 코드 구조 개선 (기능 변화 없음)

2. **WHAT을 작성한다. HOW는 작성하지 않는다.**
    - ✅ "로그인한 사용자만 북마크할 수 있다"
    - ❌ "BookmarkService에 save() 메서드 추가"

3. **"안 돼요", "이상해요"는 정보가 아니다.**
   기대 동작과 실제 동작을 분리해서 작성한다.

---

## `[feat]` — 기능 추가

```
[feat] {기능 이름}

배경: {왜 필요한가 — 1~2줄}

기능:
- {어떤 행위가 가능해야 하는가 — 주어+동사 형태}
- {복수 기능이면 항목 추가}

제약:
- {누가 사용 가능한가 — 예: 로그인한 사용자만 / 누구나}
- {중복 불가 등 비즈니스 제약 조건}
```

**API 경로나 응답 필드를 특정하고 싶을 때만 추가:**

```
설계 요구사항:
- {예: /api/v1/bills/{billId}/bookmarks 경로 사용}
- {예: 목록 응답에 createdAt 필드 포함}
```

### 작성 예시

```
[feat] 법안 북마크 기능

배경: 사용자가 관심 있는 법안을 저장해두고 나중에 다시 볼 수 있어야 함

기능:
- 로그인한 사용자가 특정 법안을 북마크할 수 있다
- 북마크를 취소할 수 있다
- 내 북마크 법안 목록을 조회할 수 있다

제약:
- MEMBER 이상만 북마크 가능
- 동일 법안에 중복 북마크 불가
- 북마크 취소는 북마크 상태인 법안에만 가능
```

### 체크리스트

- [ ] `[feat]` 태그
- [ ] 배경 (왜 필요한가)
- [ ] 기능 목록 (주어+동사 형태)
- [ ] 제약 조건 (권한, 중복 방지 등)

## `[fix]` — 버그 수정

```
[fix] {버그 제목}

상황: {어떤 기능에서, 어떤 조건에서 발생하는가}

재현:
  1. {단계 1}
  2. {단계 2}
  3. {단계 3}

기대: {어떻게 동작해야 하는가}
실제: {실제로 어떻게 동작하는가 — 에러 메시지나 HTTP 상태코드 포함}

재현율: 항상 | 간헐적 (  %)
원인: {알고 있으면 작성, 모르면 생략}
```

### 작성 예시

```
[fix] 구독 취소 후 재구독이 안 되는 버그

상황: 입법계정 구독 취소 후 동일 계정에 다시 구독 시도 시

재현:
  1. 보건복지위원회 계정 구독
  2. 구독 취소
  3. 동일 계정에 재구독 시도

기대: 정상적으로 구독 완료 (201)
실제: 409 Conflict 반환 — "이미 구독 중입니다" 메시지

재현율: 항상
원인: deactivate 상태인데 alreadySubscribed 검사가 상태를 무시하는 것 같음
```

### 체크리스트

- [ ] `[fix]` 태그
- [ ] 어떤 기능에서 발생하는지
- [ ] 재현 단계 (번호 목록)
- [ ] 기대 동작 (올바른 동작이 무엇인지)
- [ ] 실제 동작 (에러 코드 / 메시지 포함)
- [ ] 재현율

## `[refactor]` — 리팩터링

```
[refactor] {리팩터링 제목}

문제: {현재 어떤 원칙/규칙을 위반하고 있는가, 또는 어떤 설계 문제가 있는가}

목표: {어떤 상태가 되어야 하는가 — 레이어/동작 수준으로, 클래스명은 불필요}

유지: {이 작업 후에도 반드시 그대로여야 하는 외부 동작}
```

**특수한 완료 조건이 있을 때만 추가:**

```
완료 조건:
- {예: 특정 API 응답 구조가 변경되지 않아야 한다}
```

### 작성 예시

```
[refactor] NotificationSetting 도메인 객체 setter 제거

문제: NotificationSetting이 setIsNotifiable() setter를 직접 노출하고 있어
     불변 객체 원칙을 위반하고 있음

목표: setter를 제거하고 activate() / deactivate() 메서드로 새 인스턴스를 반환하도록
     LegislationAccount의 with 패턴과 동일한 구조로 변경

유지: 알림 켜기/끄기 API의 외부 동작은 변경되지 않아야 함
```

### 체크리스트

- [ ] `[refactor]` 태그
- [ ] 현재 문제점 (어떤 원칙/규칙 위반인가)
- [ ] TO-BE 목표 상태
- [ ] 변경 후에도 유지돼야 하는 동작

## 자주 하는 실수

| 잘못된 예 | 문제 | 올바른 방향 |
|---|---|---|
| "리액션 기능 추가해주세요" | 기능/제약 정보 없음 | 기능 목록과 제약 조건 작성 |
| "BookmarkRepository 추가해주세요" | HOW 수준 (구현 지시) | WHAT 수준으로 — "북마크를 저장할 수 있어야 한다" |
| "구독이 이상해요" | 기대/실제 동작 구분 없음 | 기대 동작과 실제 동작을 분리해서 작성 |
| "서비스 레이어 정리 필요해요" | 문제점/목표 불명확 | AS-IS 문제점과 TO-BE 목표를 구체적으로 |
